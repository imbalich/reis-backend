# Product Config Code 全链路切换设计

**日期：** 2026-04-16

**背景**

当前系统原有业务分层口径为：

- `产品`
- `产品 + 零部件`

实际业务已切换为新的正式分析维度：

- `产品 + 派生码(product_config_code)`
- `产品 + 派生码(product_config_code) + 零部件`

本次调整不是新增一个展示字段，而是替换主分析键。凡是依赖分析对象识别、分层统计、拟合结果、计算结果、任务执行和结果查询的链路，都需要随之切换。

---

## 1. 本次整改目标

本次整改的目标是将首批优先闭环 `datamanage -> fit -> calcu` 全面切换到新口径，使系统后续新导入数据、新触发任务、新生成结果均按 `product_config_code` 参与正式业务分层。

整改后的正式业务对象定义为：

- 整机分析对象：`product + product_config_code`
- 零部件分析对象：`product + product_config_code + part`

`product_config_code` 必须作为正式分析键参与：

- 基础数据入库与查询
- 样本筛选
- 分组统计
- 拟合任务执行
- 拟合结果写入与读取
- 计算任务执行
- 计算结果写入与读取

---

## 2. 本次整改范围

### 2.1 纳入本次整改的模块

本次只覆盖首批必须打通的主链路：

- `backend/app/datamanage`
- `backend/app/fit`
- `backend/app/calcu`

### 2.2 暂不纳入本次整改的模块

以下模块不在首批闭环内，只保留后续整改清单，不在本次设计内展开：

- `sense`
- `degrade`
- `lifetime`
- `lcc`
- `rcm`
- `rbd`
- 其他非首批主链路插件和扩展模块

---

## 3. 业务边界与兼容策略

### 3.1 口径切换方式

本次采取一次性完全切换到新口径，不保留长期双轨兼容。

系统目标形态不是：

- 旧口径继续可运行
- 新旧口径由配置切换
- 对外长期保留两套结果

系统目标形态是：

- 新数据进入后，后续全链路只按新口径运行
- 旧口径不再作为目标业务路径

### 3.2 历史数据处理策略

历史结果不做追溯重算。

本次只保证：

- 新导入数据按新口径入库
- 新触发计算按新口径执行
- 新结果按新口径落库与查询

历史存量底层数据将由人工后续迁移并重刷库，应用代码不承担在线历史迁移和兼容适配逻辑。

### 3.3 应用侧约束

应用需要提前具备以下能力：

- 数据库结构可承载 `product_config_code`
- 模型、Schema、接口、任务、结果链路全部接受新维度
- 不依赖旧数据兼容分支才能运行

---

## 4. 总体整改思路

本次整改不采用“字段渗透式零散补丁”，而采用“先定义正式分析键，再按分析键重构主链路”的方式推进。

正式分析维度统一定义为两类：

- `product_dimension = product + product_config_code`
- `part_dimension = product + product_config_code + part`

后续所有涉及“识别一个分析对象”的逻辑，都必须围绕这两个维度实现，而不是继续默认使用旧口径。

本次整改关注点不是“把字段接进去”，而是“把主分析维度改掉”。

---

## 5. 模块设计

### 5.1 datamanage

`datamanage` 在本次整改中的职责，不再只是承载基础业务数据，而是为下游 `fit` 与 `calcu` 提供符合新维度定义的标准化数据入口。

本模块需要完成以下调整：

- 所有进入主分析链路的基础数据表补齐 `product_config_code`
- 相关 `model / schema / crud / service / api` 接入该字段
- 所有供 `fit / calcu` 调用的数据查询服务切换为按新维度筛选
- 所有去重、归并、更新、查重和唯一性判断逻辑纳入 `product_config_code`
- 对关键分析输入数据建立最小可验证样本

整改后的要求是：同一 `product` 下，不同 `product_config_code` 的数据可以同时存在、同时查询、互不覆盖。

#### datamanage 高风险点

- 表已加字段，但 service 查询仍只按 `product` 过滤，导致不同派生码样本提前混合
- 唯一约束或业务唯一判定仍基于旧口径，后写数据覆盖先写数据
- 导入流程接上字段，但下游供数 service 未按新维度返回隔离样本

### 5.2 fit

`fit` 的核心变化是重新定义“拟合对象”。

整改前：

- 整机级拟合对象：`product`
- 零部件级拟合对象：`product + part`

整改后：

- 整机级拟合对象：`product + product_config_code`
- 零部件级拟合对象：`product + product_config_code + part`

本模块需要完成以下调整：

- 所有拟合相关入参 schema 接入 `product_config_code`
- Celery 任务参数与任务函数签名同步接入 `product_config_code`
- 拟合前样本查询逻辑按新维度隔离
- 拟合结果表的写入键、查询键、更新键切换到新维度
- “最佳拟合”“指定条件查询”“批量拟合”逻辑统一切换到新维度
- 标签处理、策略处理和数据校验中涉及模型识别的逻辑同步切换

整改后的要求是：同一 `product` 下两个不同派生码可以分别拟合、分别查询、分别保留各自结果。

#### fit 高风险点

- 接口已传 `product_config_code`，任务函数签名未同步
- 任务函数签名已同步，但内部查询样本仍未使用派生码
- 结果写入按新维度，查询却仍按旧维度，导致结果串层
- “最佳结果”或“最新结果”查询遗漏派生码条件，造成返回错对象

### 5.3 calcu

`calcu` 的主要整改方向是将所有统计、预测和指标计算逻辑的聚合键切换到新维度，并确保依赖 `fit` 结果时关联键一致。

本模块需要完成以下调整：

- 所有输入样本查询纳入 `product_config_code`
- 所有统计聚合、`group by`、汇总逻辑切换到新维度
- 中间统计结果、计算结果写入键切换到新维度
- 所有结果查询、导出和接口过滤条件切换到新维度
- 依赖 `fit` 结果时，查询或关联条件同步纳入 `product_config_code`

整改后的要求是：`calcu` 结果不再按旧维度混合不同派生码对象，不发生跨派生码引用拟合结果或覆盖结果的情况。

#### calcu 高风险点

- 聚合查询漏加派生码，导致统计串层
- 结果表唯一键未改，导致不同派生码结果互相覆盖
- 依赖拟合结果时只按 `product` 或 `product + part` 关联，读到错误结果

---

## 6. 高风险漏改检查框架

本次整改必须围绕以下七个方面逐项检查。

### 6.1 库表层

重点检查：

- 基础表、结果表、中间结果表是否已有 `product_config_code`
- 字段类型、长度、可空性是否统一
- 联合唯一键、索引、更新条件是否需要升级
- 是否仍存在不同派生码写入同一记录的覆盖风险

### 6.2 Schema 层

重点检查：

- 新增、编辑、查询、任务提交相关 schema 是否接入 `product_config_code`
- 分页查询和筛选查询是否支持新维度
- 分析结果返回结构是否显式带出 `product_config_code`

### 6.3 Service 层

重点检查：

- 是否仍存在按 `product` 聚合、筛选、查找的写死逻辑
- 是否仍存在按 `product + part` 去重或归并的逻辑
- 是否存在默认按整机口径兜底，从而误合并不同派生码数据
- 是否存在在预处理阶段提前合并样本的逻辑

### 6.4 任务层

重点检查：

- 任务参数和任务函数签名是否同步接入 `product_config_code`
- 调用方与任务实现是否使用同一套新维度参数
- 批量任务循环对象是否从旧维度升级为新维度
- 幂等判断、重复提交判断、结果记录是否仍使用旧键

### 6.5 结果层

重点检查：

- 写结果时的识别键与查结果时的识别键是否一致
- “最佳结果”“最新结果”“指定条件结果”是否都纳入派生码
- 覆盖式写入逻辑是否只会更新同一新维度对象

### 6.6 接口层

重点检查：

- 查询参数是否补齐 `product_config_code`
- 接口说明和文档是否更新
- 是否仍保留只按 `product` 运行的旧目标接口路径
- 返回结果是否足够让调用方区分不同派生码对象

### 6.7 验证层

重点检查：

- 同一 `product` 下不同派生码数据可同时入库
- 拟合任务与结果在不同派生码之间完全隔离
- `calcu` 结果不会跨派生码引用和覆盖
- 查询接口按新维度能够查准

## 7. 推荐实施拆解

### 阶段 1：维度清点与影响面建模

目标是找全首批主链路中所有旧分析键使用点，形成可执行的整改映射清单。

阶段产出应包括：

- 受影响基础表清单
- 受影响结果表清单
- 受影响 schema 清单
- 受影响 service / crud / api / 任务清单
- 旧维度到新维度的替换映射

### 阶段 2：datamanage 切新口径

目标是先让主数据入口稳定产出新维度数据。

阶段完成标准：

- `product_config_code` 能进入关键基础表
- 相关查询能按新维度稳定返回数据
- 不同派生码对象互不覆盖、互不串层

### 阶段 3：fit 切新拟合对象

目标是重定义拟合对象，确保任务、样本、结果和查询全部按新维度运行。

阶段完成标准：

- 同一 `product` 下两个派生码可以独立拟合
- 拟合结果可独立写入和独立查询
- “最佳拟合”与“最新结果”不串层

### 阶段 4：calcu 切新聚合对象并闭环验证

目标是完成主链路闭环，使 `datamanage -> fit -> calcu` 在新库样本下可稳定运行。

阶段完成标准：

- `calcu` 聚合逻辑切到新维度
- `fit` 结果引用条件切到新维度
- 从基础数据到拟合再到计算的闭环样本验证通过

---

## 8. 验收标准

本次首批整改验收通过的判定标准如下：

- `datamanage` 已能稳定接收并查询 `product_config_code`
- `fit` 已按 `product + product_config_code` 与 `product + product_config_code + part` 生成和查询结果
- `calcu` 已按同一新维度完成聚合和结果读取
- 同产品不同派生码数据不会互相覆盖、互相串层、互相借用结果
- 旧口径残留历史数据不会成为当前新计算的目标路径

---

## 9. 后续阶段建议

在首批闭环稳定后，后续可继续按同样方法推进以下模块：

- `sense`
- `degrade`
- `lifetime`
- `lcc`
- `rcm`
- `rbd`

后续整改仍应沿用本设计中的核心原则：

- 先定义分析对象
- 再切换主分析键
- 最后验证结果隔离性

---

## 10. 结论

本次整改的本质不是接入一个新字段，而是把系统主分析维度从旧层级切换到新层级。

首批主线应聚焦于 `datamanage -> fit -> calcu`，以“完全切换新口径、历史结果不追溯、人工后续迁移底层数据并重刷库”为边界，优先建立新数据下可稳定运行的主业务闭环。

只要该闭环被正确切换，其余分析模块即可后续按同一范式逐步整改，而不会继续放大旧维度带来的串层和覆盖风险。
